# Design Pack — p1-mission-shell

`DESIGN PACK v1 | feature p1-mission-shell | design doc v1.15 | goals: G1..G10 | mechanics: M1..M9`
*Owner: Kimi K3. Gate: must exist before Stage 2 finalizes.*

**Versions cited (charter §8):** charter v1.13 · design doc **v1.15** (bumped doc-first from v1.14 by this pack — rulings R1–R6 landed in the §3 prototype scoping note + §10) · visual direction **v1.5** (unchanged — all presentation cites existing palette) · feature roadmap v1.7 (P1 #6) · shipped deps: `p1-deck-geometry` (deck graph, both airlocks `spawnSafe`/`breachPoint`, objectives in deck03.json incl. `obj-primary-reactor` @ engineering), `p1-enemy-baseline` (8-crew spawner, AL0/AL1 alarm stub, crew combat), `p1-combat-core` v2 (health/damage/death pipeline — its G4 3 s respawn clause is **superseded** by this pack's R4).

**Feature (roadmap P1 #6):** airlock entry sequence, objective placeholder ("reach Engineering"), mission end + score screen — **§3 Phase 0–1 shell only**. Depends on #2 + #5 ✅. This feature converts the sandbox into a mission: today the player spawns at the port airlock with combat live immediately and death respawning after 3 s; after this feature the game has a beginning (breach select → insertion), a middle (objective), and an end (complete/failed → score → restart). Resolves the deferrals recorded in `p1-enemy-baseline` (non-goal: "Mission integration: airlock sequence, objectives, fail flow") and `p1-combat-core` M5 ("mission-fail flow deferred to `p1-mission-shell`").

**Design rulings (new, this pack):**

- **R1 — Breach choice: retained, minimal form.** The Director's kickoff allowed simplifying the two-breach choice; I rule **against** dropping it. §3 Phase 0 names breach selection "the mission's first meaningful decision" and §7 rule 5 mandates exactly 2 valid breach points with asymmetric risk/reward — both airlocks already exist in deck data with `spawnSafe`/`breachPoint` flags and distinct `breachProfile`s, so the choice costs a text select, not a system. The *presentation* is what's simplified: two text options with the §3 Phase 0 profile lines, no map art, no cinematic. Full briefing UI is an explicit non-goal. *(Doc change: yes — §3 v1.15 scoping note.)*
- **R2 — Airlock entry sequence.** 5.0 s cycle from confirm: player spawns centered in the selected airlock facing the inner (spine-side) door; **all gameplay verbs locked** for the cycle (the player watches the door, nothing else); the inner door edge is closed — impassable to the player *and* crew and blocking LOS — then opens on completion and stays open for the session. One cycle number, one door behavior, no manual controls: the airlock is a scripted insertion beat, not a gameplay space (venting/manual cycling are P3+ and do not exist). *(Doc change: yes — §3 note + §10 row, v1.15.)*
- **R3 — Objective placeholder.** "Reach Engineering," issued at door-open. Completion = the **living** player entering the Engineering room footprint (not a marker radius, not an interaction — room entry is the simplest binary check and matches the roadmap's "reach Engineering" language). Presentation: transient text banner on issue + in-world beacon at `obj-primary-reactor` (allied `#69f0ae`, steady emissive marker, render-only, extinguished on completion). The bridge secondary objective exists in deck data but is **not issued** at P1 (intel is a §3 Phase 6 soft gate — P2+). *(Doc change: yes — §3 v1.15 scoping note.)*
- **R4 — Fail flow: death ends the mission.** Player HP 0 → FAILED → score screen. This **supersedes** the §10 v1.12 3 s respawn placeholder — the row is replaced in v1.15 and the respawn clause of accepted `p1-combat-core` G4 is superseded (charter §7 regression-safety note: the remainder of combat-core G4 death semantics — dead state, inert input — is unchanged and preserved). Solo-first makes death binary; co-op downed-but-not-out (§8) is netcode-era. Same-tick contention (dying while entering Engineering): **FAILED wins** — completion requires a living player. *(Doc change: yes — §10 v1.15.)*
- **R5 — Alarm integration: zero changes to the stub.** The `p1-enemy-baseline` AL0/AL1 semantics (R7 there) are exactly the §3 Phase 1 stealth window: patrol-unaware at AL0, stealth ends on first contact or first fired shot. R2's locked verbs + closed door guarantee no trip can occur during the cycle (no shots possible; no LOS exists for detection; crew can't be damaged by a locked player). The stealth window is therefore *door-open → first trip*, emergent from shipped systems. No new stealth mechanics (no takedowns, no concealment, no sensors — §3 Phase 1's camera/hull-sensor trip stays N/A at P1). *(Doc change: no — existing v1.14 note already governs.)*
- **R6 — Score screen is data, not economy.** Fields: outcome banner, breach point, mission time (clock from sim tick 0 — the cycle is included, it's constant), alarm-tripped status (+ trip time), crew neutralized x/8. **No composite score, no grades, no persistence** — a scoring economy is meta-progression design (post-prototype, §11 open questions territory) and inventing numbers here would be anti-assumption against myself. *(Doc change: yes — §3 v1.15 scoping note lists the fields.)*
- **R7 — Restart is the only continuation.** Score screen → restart → BRIEFING on a fresh sim (tick 0; 100 HP / 30+120; crew 8; AL0; objective unissued). No resume, no checkpoint, no quick-retry-that-skips-briefing — one path keeps the state machine (G1) small and the determinism story (G8/G9) clean.
- **R8 — Shell input mapping.** Reuses the §8 v1.12 verb set, no new bindings: move verb (WASD / left stick up-down) changes selection, interact (E / face-south) confirms, cancel (Esc / face-east) backs out where a back exists. Input parity (§8) applies to shell screens exactly as to gameplay; shell inputs are deterministic commands like any other (§12.1). Fire/reload do nothing on shell screens.

**Explicit non-goals (do not build):**

- §3 Phase 2–6: lockdown, blast-door sealing, CIC slice, coolant vent, two-key window, reactor arming/hold-out, escape timer, sealed-breach/reroute, repopulation, manual-crank door, off-path incentives (Armory resupply, Med Bay healing, captives, intel) — P2+. **All doors stay open passages** (deck-geometry R1) except the R2 cycle-closed airlock inner door.
- HUD — objective line, alarm indicator, health/ammo, in-mission clock: `p1-hud` (#7). The transient banner (R3) and dev overlay are the only readouts.
- Briefing UI polish beyond the minimal select: map art, ship schematic, dropship/approach cinematic, difficulty/options screens — deferred; M-P1 (#9) skins presentation.
- Ship PA announcements — `p2-ship-pa` (P2 #7). §9.1 rule 4 telegraphing arrives with it.
- Composite score, grades, persistence, unlocks, meta-progression — post-prototype design (R6).
- Co-op death rules: downed-but-not-out, revive, ≥1-player extraction (§8) — netcode era (R4).
- Reactor/charge interaction of any kind; the beacon is a marker, not an interactable (M4).
- Airlock as gameplay space: manual cycle controls, outer door, venting, depressurization — P3 systems; the cycle is a scripted beat (R2).
- Any change to combat, AI, alarm, ammo, or tuning numbers — none. `p1-enemy-baseline` G1–G10 and `p1-combat-core` G1–G10 (minus the G4 respawn clause, R4) must keep passing unmodified (regression safety, charter §7).
- Secondary objectives (bridge intel) — P2+ (R3).
- Audio — no audio system exists; flagged for phase-checkpoint scoping (combat-core precedent).
- Hero art, screen furniture, animated transitions — blockout text on palette chrome; `p1-visual-pass` (#9, M-P1) owns skinning.

## Rule spec

1. **§3 Phase 0 + v1.15 scoping note (M1, R1).** "The squad selects one of two breach points… Port → Cargo Hold/Armory, loot-rich, heavier patrol density; Starboard → Life Support/Barracks, softer initial resistance, fewer resources… the mission's first meaningful decision." P1 shell: the decision exists as the minimal select; the profiles are *informational text* — the density asymmetry already exists in the shipped spawn table (port row: Cargo + Armory posts; stbd row: Life Support + Barracks posts), so the text is true today. Both options are always available; there is no wrong-choice lockout.
2. **§3 Phase 1 + v1.15 scoping note (M2, R2/R5).** "Airlock cycle provides a stealth window: enemies are on patrol routes, unaware. Stealth ends on first contact, first camera/hull-sensor trip, or first fired shot → ALARM." The 5.0 s cycle is the scripted prologue; the stealth window proper begins at door-open and runs on the shipped AL0 stub until its first trip. The cycle's closed inner door is a temporary door state — the only closed door at P1 — and must block crew pathing/perception exactly as a wall does while closed (crew never path to or target through it).
3. **§4 v1.14 scoping note (M3, R5) — unchanged, integrated not modified.** Mission starts AL0; the three trip rules and converge-only AL1 effect behave per `p1-enemy-baseline` G7. The alarm never de-escalates. Lockdown, reinforcements, AL2+ do not exist. Score-screen alarm status (G6) reads this stub's state — trip flag + trip tick are sim data.
4. **Mission end & fail (M5/M6, R4/R6).** §10 v1.15: death = FAILED → score → restart; the v1.12 3 s respawn is gone. End states are terminal within a session: after COMPLETE or FAILED, no gameplay state changes except via restart (G8) — the sim holds the end-state tableau (corpses, alarm, positions) behind the score screen. Completion check = player alive **and** inside the Engineering room footprint that tick; fail check = player HP 0; fail precedence on contention (R4).
5. **Objective data (M4, R3).** `obj-primary-reactor` (engineering, kind primary) is the P1 objective point; `obj-secondary-bridge` exists in deck data and is **inert** — no issue, no marker, no completion logic (R3). Objectives remain topology-agnostic deck data (§12.2) — room IDs and kinds, never hard-coded coordinates in logic.
6. **Netcode-ready architecture (§12.1, non-negotiable — G9).** Mission state machine, cycle timer, objective state, end/score state, kill counter, alarm-trip tick: all sim state inside the fixed tick with command-driven transitions; shell-screen inputs enter through the same command pipeline as gameplay verbs (M8). Banner, beacon, and screens are render-only and must never feed back into sim — the combat-core G8/G10 replay pattern is the verification model.
7. **§8 input parity + v1.12 binding table (M8, R8).** Every shell action is fully operable on keyboard/mouse and gamepad with hot-swap intact; no new bindings are introduced. The binding rule holds: fire owns the primary trigger — shell confirm is interact, never fire.
8. **Visual direction v1.5 (M9, G10).** Shell screens: void chrome `#05080f` base, palette-conformant text (visual §3); objective beacon allied `#69f0ae` ("player-aligned indicators") — it is **not** an interactable, so `#ffd54f` is not used, and red never decorates (§3 rule); the banner is transient and minimal, subordinate to the §7 clarity hierarchy; beacon must stay legible against hull-steel floors without competing with interactables or telegraphs. Blockout fidelity — no new tangible assets (kit-bash path per charter overkill rule).
9. **Scope guard (anti-assumption).** A mechanic not in the callout does not exist: no lockdown, no gating, no HUD, no PA, no reactor interaction, no co-op death rules, no persistence, no scoring economy, no audio, no closed doors other than the R2 cycle door. Any of these in the PR is an anti-assumption violation and a Gate 1 blocker.

## Open questions anticipated for Stage 2 (clarification loop §3.2a)

None blocking — R1–R8 pre-rule the expected conflicts. Topics Grok may still raise, with my positions:

- **Shell input plumbing** (commands vs input-layer UI events) — Grok's call; binding constraints are §12.1 (deterministic, replayable, command-driven), §8 parity, and the R8 verb mapping.
- **Closed inner-door representation** during the cycle (door-edge state vs temporary collision/LOS blocker) — technical; design constraint: impassable to player and crew, blocks crew perception LOS, opens permanently at cycle end (M2, rule spec 2). Lockdown-era door states (P2) should find this forward-compatible, but P2 behavior must not leak in.
- **Stbd spawn data** — `computeSpawnPoint` already derives per-room spawns (port today); stbd-airlock needs the same treatment with facing toward its spine-side door. Data detail, Grok/Composer.
- **Score counters** (kill count, alarm-trip tick, mission clock) — sim-side counters, seeded-free, trivially deterministic; all three already have sim sources (crew deaths, alarm state, tick).
- **End-state sim behavior** (paused vs stepping behind the score screen) — Grok's call; design constraint: no gameplay state changes after the end state except via restart (rule spec 4).
- **Banner/beacon render layer** — render-only, zero sim coupling (G9); placement per rule spec 8.
