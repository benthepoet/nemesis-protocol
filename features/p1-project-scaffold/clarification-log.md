| 1 | **Scaffold-level action vocabulary (G5).** Design pack acceptance for G5 cites e.g. a test `interact` verb but does not enumerate the full set of scaffold-level actions that must have KBM↔gamepad parity. What is the exact closed list of `ActionId`s for this feature? Spec provisionally uses `interact` + `cancel` with bindings E/LMB/A and Escape/B. Confirm, replace, or extend that list (names + which physical controls count as the same logical action). | **Confirmed, with one refinement.** Closed `ActionId` set for this feature: `{ interact, cancel }` — nothing else. Both are button actions emitted as **press/release command pairs** (so held-state semantics, Q4, are testable). Bindings: `interact` = keyboard E / mouse LMB / gamepad south button (A/cross); `cancel` = keyboard Escape / gamepad east button (B/circle). The binding table must be data-driven, not hard-coded per device. | no |
| 2 | **Placeholder scene visual bar (G2 / Gate 1).** Pack says primitives only; visual direction §3 defines void `#05080f` and hull-steel ranges. For Gate 1 on this feature, must the placeholder clear color / material tones conform to that palette (and any minimal lighting mood), or is any lit primitive scene sufficient as long as HDR + ACESFilmicToneMapping are enabled and 60 fps @ 1080p holds? | **Palette-conformant.** Team principle (charter §0) applies even to scaffolding: clear color is void `#05080f`; primitive materials sit in the hull-steel range `#1a232e`–`#2a3644`; lighting is one warm-neutral key + one cool fill (Cruise/AL0 mood, visual direction §4.1). This is cheap, and it makes the ACES/HDR check meaningful rather than theoretical. | no |
| 3 | **G5 "byte-identical commands" — provenance fields.** Acceptance says the same scaffold action from KBM and gamepad produces byte-identical commands. Does identity include device provenance (`source: keyboard-mouse \| gamepad`), or only the logical payload (`action` + `value`)? If provenance is included, cross-device identity is impossible by definition — please rule which fields are in the parity compare. | **Commands carry no provenance.** The `InputCommand` object has no device/source field at all — the sim must be *incapable* of knowing which device an action came from. Device identity may exist only at the device-adapter layer (e.g., debug logging) and never crosses into the bus or sim. The parity compare is therefore the entire command object. | no |
| 4 | **Hot-swap held-state (G5).** On mid-session device switch, should any held/pressed state from the previous device be cleared immediately (emit release edges / zero intents), or may leftover held state from the old device continue until that device reports release? "Zero interruption" needs a concrete rule so the bus behavior is testable. | **Immediate clear.** On device disconnect or swap, the bus emits synthetic release edges for every held input of the departing device; the arriving device starts neutral. No stuck intents, ever — this is the concrete meaning of "zero interruption" (§8). | no |
| 5 | **Replay hash surface (G7).** What sim fields must be included in the final-state hash for Gate 1? Spec proposes `{ tick, nextEntityId, entities sorted by id, world meta (e.g. interactCount) }`. Confirm that set, or name any additional/excluded fields. Confirm render state is excluded. | **Confirmed as proposed.** Hash surface = `{ tick, nextEntityId, entities sorted by id (all sim-owned fields), sim-world meta }`, serialized deterministically (stable key order). Render state is excluded — the hash is a property of the sim layer only. | no |
| 6 | **G2 fps evidence for Gate 1.** Is a console-logged rolling fps sample (`[nemesis] fps=…`) sufficient observable evidence, or must the placeholder scene also show an on-canvas fps readout for Gate 1? | **On-canvas readout required.** Gate 1 evidence must be observable by me and the Director without opening devtools. A small DOM/canvas overlay showing rolling fps is mandatory; console logging may additionally exist. | no |
